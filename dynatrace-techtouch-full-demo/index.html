進行メモ（発表者用）

この場面の進め方

  • 【運用者】目安1分30秒。新任者が初めてログインした場面です。
  • 見せ場：ポップアップで役割を選ぶ → ツアーでDock・チームのダッシュボード・担当範囲（セグメント）・「問題」の場所を覚える。
  • 古いダッシュボードを開くと、ガイドが正しい1枚を案内します（構想の表現）。
  • 話すこと：この案内はSREが作り、直しているものです（場面8）。製品の使い方はDynatraceの入門コンテンツを優先し、テックタッチは「このチームのやり方」だけを案内します。
  • 問いかけ：「新任の方が一人で使えるまで、どれくらいかかっていますか」
  • 【運用者】目安1分30秒。毎朝の確認を、操作ナビで順に進めます（チェックリストの機能は前提にしていません）。
  • 見せ場：「?」のツールチップでSREが決めた目安（架空）を表示 → SLOのエラーバジェットを社内の報告基準で判断 → 同じ形で記録。
  • 話すこと：数値を見せるのはDynatrace、判断の基準を画面の上に置くのがテックタッチです。
  • 問いかけ：「毎朝の確認で、人によって見る場所や判断が違うのはどこですか」
  • 【運用者】目安2分30秒。10/1のデモ①を、担当範囲（セグメント）の設定済みの状態から始めます。
  • 比較期間に「09:00–10:00」を選ぶと、ガイドが選び直しを案内します（構想の表現）。
  • 最後に、同じ時間帯に検知された問題から場面4へつなぎます。
  • 問いかけ：「どこで迷いますか」
  • 【運用者】目安3分。10/1のデモ②に「Explain」「根本原因」「コメントでの引き継ぎ」を加えた5ステップです。
  • 話すこと：要約（Explain）・根本原因の分析・通知のワークフロー・コメントはDynatraceの機能です。テックタッチは、社内手順の順番と、社内優先度・連絡の判断・引き継ぎの書き方という会社固有のルールだけを案内します。
  • 見せ場：ステップ5の入力チェック。優先度に「高」、連絡に「運用チームにも手動でもう一度通知」を選ぶと、ガイドが止めます（ワークフローが10:03に通知済みのため重複しない。社内ルール・架空）。間違いを入力の時点で止める場面です。
  • 影響範囲の前に「ログ」や「根本原因」を開くと、社内手順の順番を案内します（構想の表現）。
  • 15分（SRE中心）では、ステップ5の引き継ぎだけを見せます（1分30秒）。
  • 問いかけ：「人によって手順や判断がばらつくのはどこですか」
  • 【SRE】目安2分30秒。運用者がDynatraceの問題に残した引き継ぎのコメントを読んで、SREが深掘りします。記録がそろっているので聞き直しません。
  • AIの分担を言い分けます：根本原因の分析・調査ガイドの推薦・DQLの作成と説明（Dynatrace Assist）はDynatraceの機能。AI Hub（構想）は社内の過去事例など、社内資料の側だけを補います。
  • 見せ場：最後に着眼点をノートブックに書き、「全員（閲覧のみ）」に共有。似た問題のとき、運用者の画面にも推薦される想定です（条件は実機で確認）。
  • Dynatrace Assistの回答は事前に確かめた例で見せます（実機）。
  • 問いかけ：「障害の深掘りの前に、運用者に聞き直していることは何ですか」
  • 【運用者】目安2分。10/1のデモ③（ダッシュボード）の発展です。SREの助言を受けて、運用者が自分で作ります。
  • 見せ場：SREのひな型を複製 → 違うひな型や期間を選ぶと選び直しを案内 → SREの確認を受けて保存。SREは確認だけをします。
  • Dynatraceの公式情報では「ひな型から作成」の機能が見当たらないため、共有したひな型を複製する形にしています。
  • 問いかけ：「ひな型選択、条件の変更、結果の検証のどこで依頼しますか」
  • 【SRE】目安2分。同じ問題が起きたらチームに知らせるワークフローを、SREが作ります。
  • 見せ場：通知先の入力チェック（個人宛て・全社向けを選ぶと案内）と、名前の命名規則「チーム_サービス_用途」の入力チェック → テスト実行 → 有効化。
  • 話すこと：全社展開では各チームが通知やSLOを作ります。SREが決めた基準を、作る人の画面でそろえます。このガイドは他のチームも使います。
  • 問いかけ：「通知やSLOの設定で、チームごとにばらつきが出ているところはありますか」
  • 【SRE】目安2分。テックタッチの管理画面（イメージ・架空）で、SREがガイドの効き目を確かめて直します。
  • 見せ場：止まっているステップ5（連絡の判断）に社内ルールの説明を足す → 持ち主と見直し日を決めて公開 → フローティングバナーで改訂を知らせる。
  • 話すこと：技術の着眼点（ログは開始5分前から見る、など）は、場面5でDynatraceの調査ガイドに残しています。テックタッチには会社のルールだけを書き、二重に管理しません。
  • 話すこと：完了率だけで自走を判断しません。Dynatraceの画面更新に合わせて点検します。動かなくなったガイドを見つける機能（AIリカバリー）は提供状況を確認中のため、聞かれたら「確認してご案内します」と答えます。
  • 数値はすべて架空で、効果を示すものではありません。推進担当を別に置く場合は、この場面を推進担当の場面にできます。
  • 問いかけ：「定着したかどうかを、どの指標で判断しますか。ガイドを直す役割は、どなたが担う想定ですか」
  • 目安1分。回数はこのデモを操作した回数です。効果の数値ではありません。
  • 「本日伺いたいこと」から、聞き手に近い視点（運用者／SRE）の問いを一つ選んで直近の具体例を伺い、最初に支援する作業を一つ決めます。

全体

  • 冒頭で「イメージデモです。画面・人物・手順・数値は架空で、実際の製品画面や連携動作を示すものではありません」とお伝えする。
  • 20分版：全場面を通す（約18分45秒）。15分（運用者中心）：場面5・7・8を口頭0:30ずつ（約13分45秒）。15分（SRE中心）：場面1・3・6を口頭0:30ずつ、場面2は省略、場面4は引き継ぎだけ（約11分15秒＋質疑）。
  • Dynatraceでできることは二重化しない。Dynatrace内で完結する支援（Explain、根本原因の分析、調査ガイドの推薦、Dynatrace Assist、通知のワークフロー、コメント）は、Dynatraceの機能として先に見せます。技術の手順はDynatraceの調査ガイドに、会社固有のルール（社内優先度・連絡の判断・書き方）はテックタッチに置きます。
  • 削減率などの数値はお約束しない。確かめ方は自力完了率・所要時間・依頼件数・再実行。

想定問答

  • 「実際のDynatrace画面で動きますか」→ ブラウザで操作するDynatraceの画面が対象です。御社環境での動作確認は導入時に実施します。
  • 「Dynatrace Assistと何が違いますか」→ Dynatrace AssistはDynatraceの情報と環境のデータを使う支援です。AI Hubは御社の社内資料の側を補う構想で、重なる部分はDynatraceの機能を優先します。
  • 「SREの手間が増えませんか」→ ガイドはよく止まる作業に絞り、画面の上の説明はノーコードで直せます。手順書と同じく持ち主と見直しの手間はかかるため、その手間と依頼件数を合わせて測ります（場面8）。
  • 「SREの基準を全チームに守ってもらえますか」→ 作る人の画面で入力チェックします（場面7）。案内だけにするか、先に進めなくするかは御社の運用ルールに合わせます。
  • 「効果はどれくらいですか」→ 現時点で数値はお約束しません。一つの作業で、自力完了率・所要時間・依頼件数を測って確かめます。
  • 「セキュリティは」→ 拡張機能の配布手続きと、AI Hubに渡す情報の範囲を御社方針に沿って決めます。AI Hubは外部のAIサービスを利用します。
