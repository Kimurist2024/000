# AI Hub 用 デモナレッジ（架空）KB01〜KB05 と プロンプト P1〜P4

このファイルは、デモ用にAI Hubのナレッジベースへ登録する**架空の社内資料**です。実在の企業・ログ・規程ではありません。
A社（架空）のSOCが持っている、と仮定した5種類の資料を、AI Hubが参照できる形に整理しています。

- AI Hubに「社内資料に基づく回答」をさせる仕組み（ナレッジベース）は、テックタッチのAI Hub特約に記載があります（検索結果の抜粋で確認。原文は構築時に確認してください）。
- デモでは実顧客のログや規程は使いません。以下のサンプルだけを登録します。
- 各KBの末尾に「AI Hubにさせる仕事」を書いています。P1〜P4のプロンプトから参照されます。

---

## KB01 SOC_LOG_DICTIONARY（ログ辞書・架空）

| 項目 | 定義 |
|---|---|
| 対象ログ | VPN認証イベント（デモでは CSV ルックアップ `demo_auth_events.csv`。本番は `index=<認証ログのインデックス>`、`sourcetype=<認証ログのsourcetype>`） |
| event_time | 認証イベントの発生時刻。書式 `%Y-%m-%d %H:%M:%S`（JST）。本番では `_time` を使う |
| src | 接続元IPアドレス。VPN装置が記録した外部側のアドレス |
| user | 認証に使われたアカウントID。社員は `姓.名` の形、特権は `admin_` で始まる、サービス用は `svc_` で始まる |
| action | `failure`（認証失敗）または `success`（認証成功）。それ以外の値は取り込み時に正規化する |
| privileged | 文字列 `true` / `false`。`admin_` で始まるアカウントは `true` |
| mfa | `approved`（多要素認証が承認された）、`not_required`、`none`（失敗イベントは `none`） |
| 注意 | `src` が社内プロキシのアドレスの場合は、接続元の特定に別のログが要る。`user` の大文字小文字は取り込み時に小文字へそろえる |

AI Hubにさせる仕事：生成されたSPLが、ここに定義された列名・値・書式だけを使っているかを照合する。定義にない列を使っていれば指摘する。

## KB02 SOC_DETECTION_STANDARD（検知基準・架空）

### 基準D-01「複数アカウントへの認証失敗の後、特権アカウントで成功」

| 項目 | 基準 |
|---|---|
| 時間枠 | 15分 |
| 失敗件数 | 同一 `src` で 10件以上 |
| 異なるアカウント数 | 同一 `src` で失敗した `user` が 5以上（`dc(user)` 相当） |
| 追加条件 | 同じ `src`・同じ特権アカウント（`privileged="true"`）で、**そのアカウントの失敗より後に** `success` がある |
| 除外 | 成功が失敗より前のケース（KB05 事例C-2024-11 を参照）。社内の脆弱性診断の送信元（別表）。 |
| 判定後の扱い | 候補は「高優先度の調査候補」とし、侵害の成立は推定しない。KB04の手順で一次調査する |
| 重大度の目安 | 特権アカウントが関わる＝高、一般アカウントだけ＝中、閾値未満＝記録のみ |

### アラートの社内基準（共通）

| 項目 | 基準 |
|---|---|
| 名前 | `SOC_<対象>_<用途>`（例：`SOC_VPN_複数失敗後の特権成功`） |
| 実行 | 15分ごとの定期実行。リアルタイム検索は使わない |
| 抑制 | 同じ `src` について60分 |
| 通知先 | チームの共有アドレス（個人アドレスは不可）。「トリガーされたアラートに追加」も付ける |
| 変更 | 閾値の変更は、変更理由・テスト結果・承認者を記録する（KB03に版を残す） |

AI Hubにさせる仕事：SPL案が「15分」「10件」「異なる5アカウント」「同じ特権アカウント」「失敗後の成功」「除外」を表現しているかを表で点検し、足りない条件をAssistantへの修正依頼文にする。

## KB03 SOC_APPROVED_SPL（承認済み検索・架空）

| ID | 用途 | 版 | 期待結果 | 備考 |
|---|---|---|---|---|
| S-01 | 接続元IP別の認証失敗ランキング（Q1） | v1.0（2026-10-01 承認） | `src` ごとの `fail_count` と `failed_users` | ダッシュボード「SOC認証監視」の上段 |
| S-02 | 多数アカウントへの失敗の閾値候補（Q2） | v1.0 | `fail_count>=10 AND failed_users>=5` | 15分窓 |
| S-03 | 同一特権アカウントで失敗後に成功（Q3） | v1.1（今回のデモで承認する想定） | ケースAのみ | `eventstats`＋`streamstats` で前後関係を判定 |
| S-04 | 5分単位の認証推移（Q4） | v1.0 | 失敗・成功の時系列 | ダッシュボードの下段 |
| S-05 | 本番検知の骨格（Q5） | 設計中 | — | プレースホルダーを置換するまで実行しない |

AI Hubにさせる仕事：依頼内容に近い承認済み検索があれば、その再利用と変更箇所を示す。新しい検索は「承認待ち」として扱う。

## KB04 SOC_RUNBOOK_AUTH（認証系アラートの一次調査手順・架空）

L1担当者が行う順番。各項目で「確認済み」「未確認」を区別して記録する。

1. **時刻**：失敗の最初と最後、成功の時刻。時刻の前後関係（成功は失敗より後か）。
2. **対象**：接続元IP（社内か、既知のVPN拠点か、海外か）、対象アカウント（特権か、サービス用か）。
3. **MFA**：成功時のMFAの結果（`approved` / `not_required` / `none`）。`not_required` なら、その理由（除外設定）を確認。
4. **正規アクセスの確認**：本人または管理者に、該当時刻のログインを確認する（連絡先：SOC上位者経由）。
5. **影響範囲**：同じ接続元から他のアカウントへの試行（S-01）、成功後の重要操作（別ログ。Assistantに追加検索を依頼）。
6. **根拠の記録と引き継ぎ**：検索結果のリンク、確認済み事実、未確認事項を記録し、SOC上位者へ引き継ぐ。

エスカレーション基準：特権アカウントの成功を含む場合は、本人確認の結果を待たずにSOC上位者へ引き継ぐ。侵害の成立は、L1では断定しない。

AI Hubにさせる仕事：Splunkの検索結果をこの順番に当てはめ、「確認済み事実」「未確認事項」「追加検索の目的」「エスカレーション候補」を分けて整理する。

## KB05 SOC_CASEBOOK（過去の判断と誤検知の典型・架空）

| 事例ID | 概要 | 判断 | 学び |
|---|---|---|---|
| C-2024-11 | 同一IPから失敗と特権成功の両方があったが、成功は失敗より**前**だった | 誤検知。管理者の正常ログインの後に、別の誰かが同じ拠点から失敗を繰り返した | 件数だけの検索では区別できない。前後関係を条件に入れる |
| C-2025-03 | 1アカウントに18回の失敗（サービス用アカウント） | パスワード変更後のバッチの設定ミス | 異なるアカウント数の条件で、総当たりと区別する |
| C-2025-07 | 失敗4件・3アカウント | 閾値未満。記録のみ | 閾値未満も時系列には残す |
| C-2026-02 | 特権アカウントで失敗後に成功、MFAは `approved` | 本人の入力ミス。本人確認で判明 | MFAが承認済みでも、本人確認までは「候補」のまま |

AI Hubにさせる仕事：今回の候補に似た事例を示し、過去の判断理由と、今回確認すべき違いを整理する。改善案（検索の変更、基準の追記）を変更申請の形にする。

## プロンプト P1〜P4（AI Hubのガイドにそのまま設定する想定）

### P1 依頼文の整形（担当者の依頼 → Splunk AI Assistant への依頼文）

```
あなたは当社SOCのSPL作成依頼の補助担当です。KB01（ログ辞書）、KB02（検知基準）、KB03（承認済み検索）を参照し、
利用者の依頼を「目的／対象ログ／条件／時系列／期待出力／確認事項」の順に整理してください。
定義されていない列や値を作らず、KB01の項目だけを使って、Splunk AI Assistantに渡す依頼文を日本語で作成してください。
不足している情報は「担当者が選ぶ項目」として分けて表示してください。
```

### P2 SPLの業務照合（Assistant の出力 → AI Hub → Assistant への修正依頼）

```
次のSPL案を、KB01〜KB03の条件と照合してください。出力は次の4項目だけにしてください。
A. 必須条件（15分、10件以上、異なる5アカウント以上、同じ特権アカウント、失敗後の成功、除外）が、SPLのどこで表現されているか
B. 表現されていない条件と、そのために誤って一致しうるテストケース（KB05を参照）
C. Splunk AI Assistantに返す修正依頼文
D. Splunkで実行して正解データと照合するときのチェックリスト
SPLの構文が通っても業務上正しいとはみなさず、正しさは検索結果と正解データの比較で判定します。
```

### P3 一次調査の整理（Splunk の検索結果 → AI Hub）

```
次の検索結果と、KB04（一次調査手順）、KB05（過去の事例）を参照して、
1. 確認済み事実　2. 未確認事項　3. 追加検索の目的　4. エスカレーション候補
を分けて整理してください。攻撃の成立や不正を、推定だけで断定しないでください。
追加検索が必要な場合は、Splunk AI Assistantに渡す依頼文を示してください。
```

### P4 改善・再利用（クローズ → ナレッジ）

```
今回の調査で修正した検索と判断基準を、KB03（承認済み検索）とKB05（事例集）へ登録するための変更申請案にしてください。
「変更目的／変更前／変更後／期待結果／反例／確認者／承認日」を埋め、未確定の値は空欄のままにしてください。
```

## デモで見せる「模範回答」の扱い

- AI Hubの回答は、本番前に同じ入力で確かめた例を使います。その場の生成がうまくいかない場合は、確かめた例の画面に切り替えます。
- Splunk AI Assistantの出力は、そのまま表示します。特定の失敗を実出力として演出しません。不足があれば、その内容をAI Hubへ渡して補います。
