# AI Hub 用 デモナレッジ（架空）KB01〜KB08 と プロンプト P1〜P8（ES・UEBA・SOAR版：M365アカウントの乗っ取り）

このファイルは、デモ用にAI Hubのナレッジベースへ登録する**架空の社内資料**です。実在の企業・ログ・規程ではありません。架空のA社のSOCが持っている、と仮定した8種類の資料を、AI Hubが参照できる形に整理しています。

- AI Hubに「社内資料に基づく回答」をさせる仕組み（ナレッジベース）は、テックタッチのAI Hub特約に記載があります（検索結果の抜粋で確認。原文は構築時に確認してください）。
- デモでは実顧客のログや規程は使いません。以下のサンプルだけを登録します。
- 各KBの末尾に「AI Hubにさせる仕事」を書いています。P1〜P8のプロンプトから参照されます。
- AI Hubは検索結果の真偽を断定せず、侵害の範囲を推定せず、報告の要否を判断しません。それぞれ、Splunkの実行結果、人の確認、法務・CSIRTの判断に委ねます。

## KB01 M365_LOG_DICTIONARY（M365監査ログの辞書・架空）

| 項目 | 定義 |
|---|---|
| 対象ログ | Microsoft 365 の監査ログ（Entra ID のサインイン、Exchange Online、SharePoint／OneDrive）。デモでは CSV ルックアップ `demo_m365_audit.csv`。本番は `index=<M365監査ログのインデックス>`、`sourcetype=<M365監査ログのsourcetype>` |
| event_time | 発生時刻。書式 `%Y-%m-%d %H:%M:%S`（JST）。本番では `_time` |
| user | アカウントID。社員は `姓の頭文字.名字`、管理者は `it_admin`、委託先は `ext_` で始まる |
| src | 接続元IPアドレス |
| geo | 接続元の国（`国内`、`国外1`、`国外2` … 本番ではGeoIPの国コード） |
| asn | 接続元のAS番号（`AS64496` は社内。本番ではGeoIPのASN） |
| workload | `EntraID`／`Exchange`／`SharePoint` |
| action | `signin`／`inbox_rule`（受信トレイルールの作成）／`download`／`send_mail`／`signout`。デモ用に単純化した値で、本番では監査ログの実際の操作名に置き換える |
| mfa | `approved`（多要素認証を通過、またはMFA済みのセッション）。`approved` でも本人の操作とは断定しない |
| target | 操作の対象（`mailbox`、`sharepoint:営業部`、`onedrive` など） |
| record_count | ダウンロードしたファイル数、送信先の数、作成したルール数 |
| scope | `external`（社外）／`internal`（社内）。inbox_rule では転送先が社外かどうか |
| detail | 補足（ルールの内容、機密区分の内訳、メールの件名など） |
| request_id | 申請番号（移行・保守作業 `CHG-`）。空なら申請なし |
| 平常値 | `demo_m365_baseline.csv`：user ごとの `usual_geo`、`usual_asn`、役割、部署。本番ではUEBAの平常値かRBAのリスクイベントで置き換える設計も検討する |
| 注意 | 本番用の名称をAIが創作してはならない（`<…>` のまま、担当者が置き換える）。CSVルックアップの空値（`request_id=""`）は `null()` に変換してから集計する（Splunk実機で要確認） |

AI Hubにさせる仕事：生成されたSPLが、ここに定義された列名・値・書式だけを使っているかを照合する。定義にない列を使っていれば指摘する。

## KB02 M365_DETECTION_STANDARD（検知基準・架空）

| 基準 | 内容 |
|---|---|
| D-02 M365アカウントの乗っ取りの疑い | 普段と違う接続元（国またはASNが平常値と違う）からのサインインの後60分以内に、同じアカウントが外部への転送ルール（scope=external の inbox_rule）を1件以上作成し、ファイルを合計500件以上ダウンロードした |
| 例外 | 申請番号（request_id）のある移行・保守作業は除外する。ただし、作業後に転送ルールが削除されたかは別途確認する |
| ESの設定 | 相関検索の名前は `SOC_対象_用途`（例：`SOC_M365_乗っ取り_D-02`）。実行間隔は15分ごと（cron）。リアルタイムは使わない。リスクスコア80、リスクオブジェクトは user。ノータブルの緊急度は「高」。抑制は同じ user で60分 |
| 判定区分 | 誤検知＝条件は満たすが脅威ではない／正当な利用＝本人の利用と確認できた（申請番号あり、または本人・上長が利用を確認）／要対応＝インシデントとして対応する。本人・上長が利用を否定した場合は「要対応」 |
| 時刻 | Splunk Cloudのスケジュール時刻はUTC |

AI Hubにさせる仕事：依頼文とSPL案に、D-02の条件（普段と違う接続元・60分・外部への転送ルール・500件・申請済みは除外）が入っているかを照合する。

## KB04 M365_TRIAGE_PROCEDURE（一次調査手順：M365アカウント・架空）

1. ノータブルを開き、**担当者を自分にする**（状態を「進行中」に）。委託先待ちにしない。
2. チェックリスト7項目を「確認済み」か「未確認」で埋める：①時刻（サインイン〜最後の操作）②対象アカウント・接続元（国・ASN）③MFAの結果 ④操作の範囲（転送ルール・ダウンロード・送信）⑤本人・上長への確認（出張・利用の有無）⑥入口の裏付け（フィッシングメールの特定）⑦影響範囲（他アカウント・社外への送信）。
3. 上長には社内チャットで次の文面を送る。本人には**メールではなく電話で**確認する（メールボックスが乗っ取られている可能性があるため）：「{日時} に、{user} さんのアカウントで {国} からのサインインがあり、{操作の要約} が行われています。出張や海外からの利用の予定はありますか。本人には、メールではなく電話で確認してください。」
4. 判定区分（KB02）を決める。本人・上長が利用を否定し、外部への転送ルールがある場合は「要対応」として、入口の裏付けを待たずに封じ込め①②へ進み、③はSOC責任者の承認を取る（KB06）。
5. 未確認の項目は「未確認」のまま引き継ぐ。空欄のまま封じ込めに進まない。侵害の範囲は推定しない。

AI Hubにさせる仕事：ノータブルの内容から、確認済み事実・追加の確認・本人と上長への確認文・判断の進め方を分けて出す（P3）。

## KB06 M365_RESPONSE_AUTHORITY（対応権限表・架空）

| アクション | 承認者 | SLA（案） |
|---|---|---|
| ①サインインセッションの失効（Entra ID） | SOC担当者の判断で即時 | — |
| ②転送ルールの無効化、パスワードリセット、MFA再登録 | SOC担当者の判断で即時 | — |
| ③アカウントの一時停止（Entra ID） | SOC責任者の承認（承認チケット番号を入力） | 30分（改善候補） |
| ④テナント全体の外部自動転送の禁止 | CSIRT責任者の承認（全社の業務に影響するため、情報システム部門と協議） | — |

例外アカウント：`it_admin01`、`exec_*`（役員）。③以降は必ず責任者に確認する。承認者不在時の代理は改善候補。

AI Hubにさせる仕事：対象アカウントが例外に該当するか、各アクションの承認者、いま実行してよい範囲を表で出す（P5）。

## KB07 M365_NOTIFICATION_BASIS（通知・報告の判断材料・架空）

記録は次の4項目で残す：事象／確認済み／未確認／対応。通知・報告の判断材料として、次を確認済みと未確認に分けて書く。

| 項目 | 確認済みに書くこと | 未確認に残すこと |
|---|---|---|
| ダウンロード | 件数と機密区分の内訳、対象のサイト | ファイルの中身（個人情報を含むか） |
| 外部への転送 | 転送ルールの作成時刻と無効化の時刻 | ルール作成以降に転送されたメールの件数 |
| 社内・社外への送信 | 送信先の数、件名 | リンクを開いた人と、そのアカウント |
| 他アカウント | 同じ接続元からのサインインの有無（検索の範囲を明記） | 別の接続元からの広がり |
| 封じ込め | 実行したアクションと承認番号 | 未実行のアクションと判断者 |

監督官庁への報告と公表の要否は、法務とCSIRTがこの記録をもとに判断する。SOCは判断しない。「0件」は「この範囲では確認されない」と書き、言い切らない。

AI Hubにさせる仕事：Q4a・Q4bの結果と一次対応の記録から、この表を埋める（P7）。報告の要否は判断しない。

## KB08 M365_RACI_WITH_VENDOR（委託先との役割分担・架空）

| 工程 | これまで | これから |
|---|---|---|
| 夜間監視・高度な分析・フォレンジック | 委託先 | 委託先（変更なし） |
| ノータブルの一次対応・本人確認 | 委託先 → A社に問い合わせ | A社SOC担当者（KB04） |
| 封じ込めの判断・承認 | 決まっていない | ①②SOC担当者、③SOC責任者、④CSIRT責任者（KB06） |
| 検知ルールの変更 | 委託先の見積もり・改修 | A社SOCが作り、委託先がレビュー（KB02・KB03） |
| 範囲の確定・記録 | 委託先の分析待ち | A社SOCが標準検索で確定し、記録（KB07） |

AI Hubにさせる仕事：委託先待ちになった工程を社内が担う形に、この表を書き換える案を作る（P8）。委託先に残す工程も示す。

## プロンプト P1〜P8（担当者の入力の例文）

- **P1 要件整理**：「次の依頼を、KB01（ログ辞書）・KB02（検知基準）・KB03（承認済み検索）に照らして、対象・条件・例外・確認事項・分析の分け方に整理し、Splunk AI Assistant向けの依頼文（列名と書式を含む）を作ってください。」
- **P2 照合**：「次のSPL案を、KB01〜KB03と照合してください。①参照するログ・フィールド、②普段と違う接続元の判定、③60分の窓、④外部への転送ルール、⑤申請済みの例外を表で評価し、不足箇所についてAssistantへの修正依頼文を作ってください。検索結果の真偽は断定せず、実データで確認する項目を示してください。」
- **P3 一次調査の整理**：「ケース{内容}。KB04のM365アカウント手順に従って、確認済み事実・追加の確認事項・本人と上長への確認の文面・エスカレーション基準を整理してください。侵害の範囲は推定しないでください。」
- **P4 ナレッジ反映**：「今回の検知条件、一次対応、封じ込めの承認段階、範囲確定の記録を、KB03・KB05・KB06に反映する変更申請の案を作ってください。SIEMの外の改善（外部自動転送の既定、MFAの方式）は要望として分けてください。承認者と見直し日を含めてください。」
- **P5 承認段階の照合**：「対象アカウント {user}、接続元 {src}、操作 {内容}。KB06の対応権限表に照らし、例外アカウントかどうか、プレイブックの各アクションの承認者と、いま実行してよい範囲を示してください。」
- **P6 範囲確定の検索案**：「{user} と {src} について、乗っ取られた間の操作（転送ルール・ダウンロード・送信）を種類別に件数・対象・詳細・時刻で確定し、同じ接続元から他のアカウントへのサインインがあるかを確かめる検索の依頼文を、KB03に沿って作ってください。」
- **P7 通知・報告の判断材料**：「Q4a・Q4bの結果と一次対応の記録から、KB07の通知・報告の判断材料を、確認済みと未確認に分けて整理してください。報告の要否は判断しないでください。」
- **P8 役割分担の書き換え**：「今回の事案で委託先待ちになった工程を、社内が担う形にKB08の役割分担表を書き換える案を作ってください。委託先に残す工程も示してください。」
