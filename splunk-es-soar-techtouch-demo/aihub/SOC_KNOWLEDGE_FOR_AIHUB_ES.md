# AI Hub 用 デモナレッジ（架空）KB01〜KB08 と プロンプト P1〜P8（ES・UEBA・SOAR版）

このファイルは、デモ用にAI Hubのナレッジベースへ登録する**架空の社内資料**です。実在の企業・ログ・規程ではありません。架空のA社（生命保険）のSOCが持っている、と仮定した8種類の資料を、AI Hubが参照できる形に整理しています。

- AI Hubに「社内資料に基づく回答」をさせる仕組み（ナレッジベース）は、テックタッチのAI Hub特約に記載があります（検索結果の抜粋で確認。原文は構築時に確認してください）。
- デモでは実顧客のログや規程は使いません。以下のサンプルだけを登録します。
- 各KBの末尾に「AI Hubにさせる仕事」を書いています。P1〜P8のプロンプトから参照されます。
- AI Hubは検索結果の真偽を断定せず、侵害の成立を推定せず、報告の要否を判断しません。それぞれ、Splunkの実行結果、人の確認、法務・CSIRTの判断に委ねます。

## KB01 HR_LOG_DICTIONARY（人事システム監査ログの辞書・架空）

| 項目 | 定義 |
|---|---|
| 対象ログ | 人事システム（HR-Portal・架空）の監査ログ。デモでは CSV ルックアップ `demo_hr_audit.csv`。本番は `index=<人事システム監査ログのインデックス>`、`sourcetype=<人事システムのsourcetype>` |
| event_time | 発生時刻。書式 `%Y-%m-%d %H:%M:%S`（JST）。本番では `_time` |
| user | アカウントID。人事部の一般は `hr_ops`、管理者は `hr_admin`、給与は `payroll`、委託先保守は `vendor_mnt` で始まる |
| src | 接続元IPアドレス |
| geo | 接続元の国（`国内`、`国外1`、`国外2` … 本番ではGeoIPの国コード） |
| asn | 接続元のAS番号（`AS64496` は社内。本番ではGeoIPのASN） |
| action | `signin`／`view`／`export`／`signout` |
| mfa | `approved`（多要素認証を通過）、`failed`、`not_applicable`。`approved` でも本人の操作とは断定しない |
| dataset | `employee_master`（在籍）、`retiree_master`（退職者） |
| record_count | 参照・エクスポートしたレコード数 |
| scope | `current`（在籍）、`retired`（退職者） |
| fields | エクスポートした項目（カンマ区切り） |
| request_id | 申請番号（人事異動の一斉処理 `HR-`、委託先の保守 `MNT-`）。空なら申請なし |
| 平常値 | `demo_hr_baseline.csv`：user ごとの `usual_geo`、`usual_asn`、役割、部署。本番ではUEBAの平常値かRBAのリスクイベントで置き換える設計も検討する |
| 注意 | 本番用の名称をAIが創作してはならない（`<…>` のまま、担当者が置き換える）。CSVルックアップの空値（`request_id=""`）は `null()` に変換してから集計する（Splunk実機で要確認） |

AI Hubにさせる仕事：生成されたSPLが、ここに定義された列名・値・書式だけを使っているかを照合する。定義にない列を使っていれば指摘する。

## KB02 HR_DETECTION_STANDARD（検知基準・架空）

| 基準 | 内容 |
|---|---|
| D-02 人事システムの異常参照 | 普段と違う接続元（国またはASNが平常値と違う）からのサインインの後60分以内に、同じアカウントが人事システムで合計1,000件以上を参照・エクスポートし、退職者データ（scope=retired）を1件以上含む |
| 例外 | 申請番号（request_id）のある一斉処理・保守作業は除外する。ただし退職者データのエクスポートは、申請があっても別途記録する |
| ESの設定 | 相関検索の名前は `SOC_対象_用途`（例：`SOC_人事_異常参照_D-02`）。実行間隔は15分ごと（cron）。リアルタイムは使わない。リスクスコア80、リスクオブジェクトは user。ノータブルの緊急度は「高」。抑制は同じ user で60分 |
| 判定区分 | 誤検知＝条件は満たすが脅威ではない／正当な利用＝本人の業務と確認できた（申請番号あり）／要対応＝インシデントとして対応する。本人確認と人事部の業務確認がそろうまでは「要対応（暫定）」 |
| 時刻 | Splunk Cloudのスケジュール時刻はUTC |

AI Hubにさせる仕事：依頼文とSPL案に、D-02の条件（普段と違う接続元・60分・1,000件・退職者を含む・申請済みは除外）が入っているかを照合する。

| 名前 | 用途 | 版 |

## KB04 HR_TRIAGE_PROCEDURE（一次調査手順：人事システム・架空）

1. ノータブルを開き、**担当者を自分にする**（状態を「進行中」に）。委託先待ちにしない。
2. チェックリスト7項目を「確認済み」か「未確認」で埋める：①時刻（サインイン〜最後のエクスポート）②対象アカウント・接続元（国・ASN）③MFAの結果 ④参照範囲（件数・退職者区分）⑤人事部の業務確認（申請の有無）⑥本人確認（本人の操作か）⑦影響範囲（顧客情報・他システム）。
3. 人事部への業務確認は、次の文面で社内チャットに送る：「{日時} に、アカウント {user} で在籍・退職者データのエクスポート（計 {件数}）が行われています。この時間帯に申請済みの一斉処理・保守作業はありますか。該当する申請番号があれば教えてください。本人への確認もお願いします。」
4. 判定区分（KB02）を決める。人事部の回答が「申請なし」で退職者データを含む場合は、本人確認を待たずに「要対応（暫定）」として封じ込め①②へ進み、③はSOC責任者の承認を取る（KB06）。
5. 未確認の項目は「未確認」のまま引き継ぐ。空欄のまま封じ込めに進まない。侵害の成立は推定しない。

AI Hubにさせる仕事：ノータブルの内容から、確認済み事実・追加の確認・人事部への問い合わせ文・判断の進め方を分けて出す（P3）。

| アクション | 承認者 | SLA（案） |
|---|---|---|
| ①セッション失効（人事システム） | SOC担当者の判断で即時 | — |
| ②パスワードリセットとMFA再登録 | SOC担当者の判断で即時 | — |

## KB07 HR_NOTIFICATION_BASIS（通知・報告の判断材料・架空）

記録は次の4項目で残す：事象／確認済み／未確認／対応。通知・報告の判断材料として、次を確認済みと未確認に分けて書く。

| 項目 | 確認済みに書くこと | 未確認に残すこと |
|---|---|---|
| 対象者数・区分 | エクスポートされた件数（在籍・退職者） | 重複、退職年の分布 |
| 項目 | エクスポートされた項目 | — |
| 顧客情報 | 顧客系システムへのアクセスの有無（検索の範囲を明記） | 他の経路・他アカウント |
| 二次被害 | — | 外部への流出の有無、悪用の兆候 |
| 封じ込め | 実行したアクションと承認番号 | 未実行のアクションと判断者 |

監督官庁への報告と公表の要否は、法務とCSIRTがこの記録をもとに判断する。SOCは判断しない。「0件」は「この範囲では確認されない」と書き、言い切らない。

AI Hubにさせる仕事：Q4a・Q4bの結果と一次対応の記録から、この表を埋める（P7）。報告の要否は判断しない。

## KB08 HR_RACI_WITH_VENDOR（委託先との役割分担・架空）

| 工程 | これまで | これから |
|---|---|---|
| 夜間監視・高度な分析・フォレンジック | 委託先 | 委託先（変更なし） |
| ノータブルの一次対応・業務確認 | 委託先 → A社に問い合わせ | A社SOC担当者（KB04） |
| 封じ込めの判断・承認 | 決まっていない | ①②SOC担当者、③SOC責任者、④CSIRT責任者（KB06） |
| 検知ルールの変更 | 委託先の見積もり・改修 | A社SOCが作り、委託先がレビュー（KB02・KB03） |
| 範囲の確定・記録 | 委託先の分析待ち | A社SOCが標準検索で確定し、記録（KB07） |

AI Hubにさせる仕事：委託先待ちになった工程を社内が担う形に、この表を書き換える案を作る（P8）。委託先に残す工程も示す。

## プロンプト P1〜P8（担当者の入力の例文）

- **P1 要件整理**：「次の依頼を、KB01（ログ辞書）・KB02（検知基準）・KB03（承認済み検索）に照らして、対象・条件・例外・確認事項・分析の分け方に整理し、Splunk AI Assistant向けの依頼文（列名と書式を含む）を作ってください。」
- **P2 照合**：「次のSPL案を、KB01〜KB03と照合してください。①参照するログ・フィールド、②普段と違う接続元の判定、③60分の窓、④退職者区分、⑤申請済みの例外を表で評価し、不足箇所についてAssistantへの修正依頼文を作ってください。検索結果の真偽は断定せず、実データで確認する項目を示してください。」
- **P3 一次調査の整理**：「ケース{内容}。KB04の人事システム手順に従って、確認済み事実・追加の確認事項・人事部への業務確認の文面・エスカレーション基準を整理してください。侵害の成立は推定しないでください。」
- **P4 ナレッジ反映**：「今回の検知条件、一次対応、封じ込めの承認段階、範囲確定の記録を、KB03・KB05・KB06に反映する変更申請の案を作ってください。SIEMの外の改善（退職者データの保持期間・参照権限）は要望として分けてください。承認者と見直し日を含めてください。」
- **P5 承認段階の照合**：「対象アカウント {user}、接続元 {src}、参照範囲 {内容}。KB06の対応権限表に照らし、例外アカウントかどうか、プレイブックの各アクションの承認者と、いま実行してよい範囲を示してください。」
- **P6 範囲確定の検索案**：「{user} と {src} について、閲覧・エクスポートされたレコードをデータセット別に件数・項目・時刻で確定し、顧客系システムに同じアカウント・接続元のアクセスがあるかを確かめる検索の依頼文を、KB03に沿って作ってください。」
- **P7 通知・報告の判断材料**：「Q4a・Q4bの結果と一次対応の記録から、KB07の通知・報告の判断材料を、確認済みと未確認に分けて整理してください。報告の要否は判断しないでください。」
- **P8 役割分担の書き換え**：「今回の事案で委託先待ちになった工程を、社内が担う形にKB08の役割分担表を書き換える案を作ってください。委託先に残す工程も示してください。」
